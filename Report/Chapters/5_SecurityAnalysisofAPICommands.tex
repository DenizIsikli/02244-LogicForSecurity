\section{Security Analysis of API Commands}

\subsection{Proof Structure}

We argue security at two levels:
\begin{itemize}
    \item \textbf{Local command preservation}: each API command preserves global flow invariants.
    \item \textbf{Trace composition}: if every step preserves invariants, whole execution traces are secure.
\end{itemize}

Invariants used below:
\begin{itemize}
    \item \textbf{I1 Label validity}: every stored object has a well-formed decentralized label.
    \item \textbf{I2 Read safety}: reads are served only to principals permitted by confidentiality policies.
    \item \textbf{I3 Write safety}: writes accepted only when integrity constraints allow them.
    \item \textbf{I4 Program safety}: user code executes only after successful flow checking.
    \item \textbf{I5 Declassification safety}: confidentiality relaxation only through authority-checked trusted transforms.
\end{itemize}

\subsection{Program-Level Flow Condition}

Let $\Gamma$ map variables to decentralized labels and $pc$ denote control-context label.

Assignment rule:
\[
\Gamma,pc \vdash x := e \quad \text{iff} \quad \Gamma \vdash e:L_e \land (pc \sqcup L_e \sqsubseteq \Gamma(x))
\]

This ensures both explicit and implicit dependencies are legal flows under decentralized labels.

\subsection{Command-by-Command Preservation Arguments}

\textbf{UPLOAD preserves I1}. Labels are parsed and validated before object creation. Invalid labels are rejected.

\textbf{READ\_DATA preserves I2}. Server returns data only if requester is in the allowed reader sets implied by confidentiality policies. Otherwise request fails without data release.

\textbf{WRITE\_DATA preserves I3}. Server checks writer trust constraints before mutation. Unauthorized writers cannot modify protected objects.

\textbf{UPLOAD\_PROGRAM preserves I4}. Unsafe source code is rejected at check time; no executable artifact is installed.

\textbf{RUN\_PROGRAM preserves I4}. Call-time label constraints are checked against inferred interface and required output label lower bound; execution occurs only when constraints hold.

\textbf{DECLASSIFY\_AND\_RELEASE preserves I5}. The command checks authority over every relaxed owner policy and enforces transform-specific restrictions. Without authority proof, no downgrade happens.

\textbf{AUDIT\_QUERY supports I5 accountability}. Every declassification event is queryable by authorized auditors, enabling post hoc verification of policy compliance.

\subsection{Representative Illegal Flows and Blocking Point}

\textbf{Case A: explicit read-down in user code.}
Blocked during \texttt{UPLOAD\_PROGRAM} static checking.

\textbf{Case B: implicit leak via branch on secret.}
Blocked by $pc$-aware assignment check.

\textbf{Case C: unauthorized data overwrite by low-trust principal.}
Blocked by \texttt{WRITE\_DATA} integrity-policy check.

\textbf{Case D: direct relabel to wider reader set without authority.}
Blocked by \texttt{DECLASSIFY\_AND\_RELEASE} authority check.

\subsection{Trace-Level Theorem}

\textbf{Theorem (API Trace Security under Assumptions).}
Assume secure authenticated transport, trusted server enforcement code, and correct implementation of command checks specified in Chapter 4. Then any trace of accepted API calls preserves invariants I1--I5 and cannot produce illegal confidentiality or integrity flows except those explicitly permitted by authority-checked declassification.

\textbf{Proof sketch.}
By induction over trace length. Base case: empty trace satisfies invariants vacuously. Inductive step: each command preserves invariants as shown above. Therefore all finite traces preserve them.

\subsection{Limitations}

The theorem does not cover:
\begin{itemize}
    \item compromised server runtime or keys,
    \item absence of all covert channels,
    \item legal/organizational misuse outside encoded policy checks.
\end{itemize}

These boundaries are explicitly reported so claims remain precise and defensible.
