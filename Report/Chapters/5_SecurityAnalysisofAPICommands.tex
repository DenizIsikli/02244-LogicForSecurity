\section{Security Analysis of API Commands}

\subsection{From Local Rules to System Guarantees}

Our argument has two levels:
\begin{itemize}
    \item \textbf{Program level}: typing rules enforce non-interference for accepted programs.
    \item \textbf{API level}: command preconditions prevent unsafe state transitions.
\end{itemize}

A trace is secure if every command instance satisfies its local rule and no command bypasses the enforcement path.

\subsection{Typing Semantics Used in Analysis}

Let $\Gamma$ map variables to lattice levels and let $pc$ denote control context level.

Assignment rule:
\[
\Gamma \vdash x := e \quad \text{iff} \quad (\Gamma \vdash e : \tau_e) \land (pc \sqcup \tau_e \sqsubseteq \Gamma(x))
\]

Interpretation: an assignment is safe only if both data dependency ($\tau_e$) and control dependency ($pc$) are no more confidential than the destination.

\subsection{Theorem-Style Guarantees}

\textbf{Proposition 1 (Accepted Program Non-Interference).}
Given fixed low inputs, if program $P$ type-checks under the above rule, changing high inputs cannot change low-observable outputs.

\textbf{Justification.}
Induction over program structure:
\begin{itemize}
    \item base cases (assignments) satisfy lattice constraint directly,
    \item sequential composition preserves constraints,
    \item conditionals/loops propagate secret dependence into $pc$, preventing writes to lower levels.
\end{itemize}

\textbf{Proposition 2 (Safe Rejection Property).}
If type-checking fails, the server executes no user code and emits no derived output object.

\textbf{Security significance.}
Potential leaks are transformed into denied requests, preserving confidentiality by refusing unsafe computation paths.

\subsection{Command-by-Command Security Argument}

\textbf{READ}. Security depends on two checks: policy authorization and channel endpoint authentication.\
If either is missing, confidentiality can fail (unauthorized read or man-in-the-middle disclosure). With both present, output remains at original label.

\textbf{WRITE}. Security depends on write authorization plus integrity policy.\
This prevents low-trust principals from corrupting high-trust records and preserves G3.

\textbf{RUN\_PROGRAM}. Security depends on strict pre-execution typing and no fallback execution mode.\
This command is the main defense against insider exfiltration code.

\textbf{RELABEL}. Security depends on approved transform, parameter bounds, and audit logging.\
Without these, RELABEL would invalidate non-interference globally.

\subsection{Representative Attack Cases}

\textbf{Case 1: Explicit leak attempt}
\begin{verbatim}
public_out := private_record
\end{verbatim}
Rejected because High $\sqsubseteq$ Low is false.

\textbf{Case 2: Implicit branch leak}
\begin{verbatim}
if private_record.flag then public_out := 1 else public_out := 0
\end{verbatim}
Rejected because $pc=\text{High}$ in both branches, so writing to Low fails.

\textbf{Case 3: Replay of old RELABEL request}
Replayed transport message is ineffective when channel/session integrity and freshness checks are enforced and request identifiers are audited. This links channel assumptions to application safety.

\subsection{What Verification Does and Does Not Prove}

The analysis supports:
\begin{itemize}
    \item confidentiality against modeled network and insider-program attacks,
    \item integrity of high-trust state under command checks,
    \item explicit localization of permitted downgrades.
\end{itemize}

It does not prove:
\begin{itemize}
    \item security under server compromise,
    \item absence of all covert channels,
    \item organizational correctness of declassification approvals.
\end{itemize}

These boundaries are necessary for honest correspondence between theorem assumptions and real deployment claims.
