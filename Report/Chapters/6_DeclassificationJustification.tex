\section{Declassification Justification and Policy Constraints}

Strict non-interference disallows all High $\rightarrow$ Low flows. Real deployments still need controlled release (for example research statistics). Therefore declassification is treated as a privileged and auditable exception, not a normal operation.

\subsection{Security Rule for Declassification}

A downgrade is accepted only as:
\[
\frac{\text{approved}(T) \land \text{params\_valid}(T,\theta) \land \text{authorized}(u)}
   {\Gamma \vdash \text{declassify}_{T,\theta}(h\!:\!\text{High}) : \text{Low}}
\]

Interpretation: changing the label is permitted only when transformation type, parameters, and caller privileges all satisfy policy.

\subsection{Approved Transformation Families}

\textbf{Redaction}. Remove fields that directly identify persons (name, id, address).\
Why it helps: it removes direct identifiers, reducing straightforward linkage attacks.

\textbf{Aggregation}. Release only group-level summaries.\
Why it helps: individuals are hidden inside population-level values; direct record reconstruction becomes harder.

\textbf{$k$-anonymization}. Enforce equivalence classes of size at least $k$.\
Why it helps: bounds single-record uniqueness under quasi-identifiers; policy can require minimum $k$ before release.

\textbf{Differential privacy}. Add calibrated noise to query results.\
Why it helps: limits how much any one person changes released output; supports formal privacy accounting through budget parameter $\epsilon$.

\subsection{Policy Parameters (Concrete and Checkable)}

To avoid superficial "approved transform" claims, the policy must define concrete thresholds:
\begin{itemize}
  \item minimum group size ($k \geq k_{min}$),
  \item maximum privacy budget per dataset ($\epsilon \leq \epsilon_{max}$),
  \item allowed query classes (no unrestricted row-level predicates),
  \item logging requirements (who approved, why, and on what dataset version).
\end{itemize}

These constraints are as important as the transform itself. A weak parameter choice can nullify theoretical guarantees.

\subsection{Threat-Oriented Justification}

We justify declassification against likely attacker strategies:
\begin{itemize}
  \item \textbf{Linkage attack}: combine released fields with external datasets.
  \item \textbf{Differencing attack}: compare near-identical aggregate queries.
  \item \textbf{Repeated query attack}: consume privacy budget over time.
\end{itemize}

Mitigations are policy-coupled:
\begin{itemize}
  \item redaction and generalization reduce linkage surface,
  \item minimum cohort size and query restrictions reduce differencing precision,
  \item cumulative budget tracking and cutoff enforce bounded repeated leakage.
\end{itemize}

\subsection{Compositional Risk Statement}

If outputs $O_1,\ldots,O_n$ are released under approved declassification steps, risk composes across releases. Therefore privacy budgets and audit trails are maintained per dataset and per requester, not per request in isolation.

This is the practical bridge between theory and operation: even individually safe releases can become unsafe in combination.

\subsection{Hospital Scenario Example}

Pipeline for research release:
\begin{enumerate}
  \item redact direct identifiers,
  \item enforce age-range grouping with $k$-minimum cohort size,
  \item release aggregates only,
  \item apply differential privacy with bounded $\epsilon$,
  \item record approval and privacy-budget consumption in audit log.
\end{enumerate}

Why this is acceptable: each step addresses a concrete attack path, and no step alone is treated as sufficient. This layered reasoning is stronger than claiming "anonymized therefore safe."

\subsection{Residual Risks}

Even with policy-compliant declassification, residual risk remains from background knowledge and future auxiliary datasets. We therefore claim \emph{risk reduction with bounded leakage}, not absolute anonymity. This conservative claim aligns with both the theory and real-world data release practice.
