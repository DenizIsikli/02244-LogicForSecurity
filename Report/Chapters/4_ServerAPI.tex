\section{Server API and Security Semantics}

This chapter specifies each command as a security-relevant transition. The purpose is to show not only what the API does, but why each operation preserves the goals from Chapter 2.

\subsection{Command-Level Contract Format}

For each command we define:
\begin{itemize}
    \item \textbf{Preconditions}: authentication, authorization, typing assumptions.
    \item \textbf{Transition}: state updates and generated objects.
    \item \textbf{Postconditions}: confidentiality/integrity properties preserved.
\end{itemize}

\subsection{Data and Access Commands}

\textbf{UPLOAD}$(u, d, \ell)$
\begin{itemize}
    \item Preconditions: user $u$ authenticated; label $\ell \in \{\text{Low, Medium, High}\}$.
    \item Transition: store object $o=(owner=u, data=d, label=\ell)$.
    \item Postcondition: object enters the lattice at a declared level; no downgrade occurs.
\end{itemize}

\textbf{READ}$(u, o)$
\begin{itemize}
    \item Preconditions: access policy allows $u$ for $o.label$.
    \item Transition: return value with same type as $o.label$.
    \item Postcondition: read is type-preserving; confidentiality depends on access policy correctness and authenticated channel delivery.
\end{itemize}

\textbf{WRITE}$(u, o, d')$
\begin{itemize}
    \item Preconditions: write authorization for $u$ and object $o$.
    \item Transition: update object content with integrity checks.
    \item Postcondition: no low-integrity principal can silently overwrite high-integrity state (goal G3).
\end{itemize}

\subsection{Computation Command}

\textbf{RUN\_PROGRAM}$(u, P, inputs, requested\_label)$
\begin{enumerate}
    \item Resolve each input object to type $\tau_i$ from its label.
    \item Type-check $P$ under environment $\Gamma = \{x_i : \tau_i\}$.
    \item If typing fails, reject with no execution and no output.
    \item If typing succeeds, infer output type $\tau_{out}$.
    \item Store output only with label compatible with $\tau_{out}$.
\end{enumerate}

Security rationale:
\begin{itemize}
    \item Prevents explicit and implicit leaks before runtime.
    \item Prevents users from requesting an output label lower than inferred security type.
    \item Makes security failure observable and auditable at submission time.
\end{itemize}

\subsection{Declassification Command}

\textbf{RELABEL}$(u, o, \ell_{new}, T)$ where $T$ is a transformation descriptor.

Downgrade ($\ell_{new} \sqsubset o.label$) is accepted \emph{only if}:
\begin{itemize}
    \item caller has declassification privilege,
    \item $T$ is in approved transform set,
    \item transform parameters satisfy policy constraints (for example minimum group size, privacy budget),
    \item operation is logged with justification metadata.
\end{itemize}

Without these checks, RELABEL would be a generic High $\rightarrow$ Low escape and break G1.

\subsection{Why This API Structure Matters}

A recurring failure mode in protocol/system reports is to treat API commands as neutral operations. Here, each command is a proof obligation:
\begin{itemize}
    \item \textbf{UPLOAD/READ/WRITE} enforce baseline policy consistency,
    \item \textbf{RUN\_PROGRAM} enforces non-interference for untrusted code,
    \item \textbf{RELABEL} localizes all sanctioned downgrades.
\end{itemize}

This separation is what lets us reason compositionally in the next chapter: if each command preserves an invariant, command traces preserve global security goals.
