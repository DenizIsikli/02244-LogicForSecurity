\section{Introduction}

This report presents a secure data-hosting service for medical information using the decentralized information-flow model of Myers and Liskov \cite{MyersLiskov97}. The goal is not only to describe a server API, but to give precise security arguments for why each API command preserves confidentiality and integrity.

The service supports three capabilities:
\begin{itemize}
    \item user-controlled security labels over data and program variables,
    \item policy-based sharing and collaboration,
    \item execution of user-provided programs after information-flow checking.
\end{itemize}

The core challenge is to support useful computation and controlled sharing without illegal flows. We therefore use decentralized labels with explicit owners, readers, and writers, and we model declassification using the authority mechanism required by Myers-Liskov.

\subsection{Evaluation Scope and Method}

The security argument is structured in three layers:
\begin{enumerate}
    \item \textbf{Model layer}: actors, trust assumptions, attacker model, and secure-channel assumptions.
    \item \textbf{Design layer}: API and program model choices justified against target security goals.
    \item \textbf{Verification layer}: per-command flow arguments and declassification justification.
\end{enumerate}

This structure follows the project priority that a smaller but precisely justified design is better than broad but superficial feature coverage.

\subsection{Decentralized Labels}

For confidentiality we use policies of form $o:r$, where owner $o$ allows readers in set $r$.
For integrity we use policies of form $o \leftarrow w$, where owner $o$ trusts writers in set $w$.

A full security label is a pair:
\[
L = (C, I)
\]
where $C$ is a conjunction of confidentiality policies and $I$ is a conjunction of integrity policies.

This model is decentralized because different owners can independently state constraints on the same value.

\subsection{Why Myers-Liskov for This Project}

Myers-Liskov is the appropriate basis for this project because declassification is a required feature in our hospital setting. The model provides:
\begin{itemize}
    \item decentralized confidentiality and integrity labels,
    \item static information-flow checks for user programs,
    \item explicit declassification with authority, instead of ad hoc downgrading.
\end{itemize}

This keeps the report aligned with the project instruction to use course methods and, for declassification, specifically the Myers-Liskov model.
