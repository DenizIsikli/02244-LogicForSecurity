\section{System Participants, Roles, and Assumptions}

\subsection{Actors and Trust Boundaries}

Let $\mathcal{A}$ be the set of actors that may appear in labels. In our deployment, $\mathcal{A}$ includes:
\begin{itemize}
    \item doctors (data owners),
    \item collaborating clinicians,
    \item researchers,
    \item administrators,
    \item the server principal.
\end{itemize}

Trust assumptions:
\begin{itemize}
    \item the server enforcement code is trusted,
    \item uploaded user programs are untrusted,
    \item users are authenticated over a secure channel before invoking API commands.
\end{itemize}

\subsection{Security Labels in the Decentralized Model}

Each object has label $L=(C,I)$:
\begin{itemize}
    \item confidentiality component $C=\bigwedge_i (o_i:r_i)$,
    \item integrity component $I=\bigwedge_j (o_j \leftarrow w_j)$.
\end{itemize}

Intuition:
\begin{itemize}
    \item $(o:r)$ says owner $o$ permits readers in $r$.
    \item $(o \leftarrow w)$ says owner $o$ trusts writers in $w$.
\end{itemize}

For fixed owner $o$, confidentiality flow from source to destination is allowed only when destination readers are a subset of source readers (no new readers added). For integrity, source writers must be a subset of destination writers (no increase in trust without proof).

\subsection{Attacker Model}

We assume a Dolev-Yao style network attacker outside trusted endpoints:
\begin{itemize}
    \item can intercept, replay, and reorder traffic,
    \item can initiate sessions and submit malicious programs,
    \item cannot break cryptographic primitives or compromise trusted server internals.
\end{itemize}

We additionally consider an insider misuse attacker: a valid user who attempts illegal flow through crafted source code or strategic API call sequences.

\subsection{Channel Abstraction and Justification}

The API assumes a secure channel equivalent to TLS with endpoint authentication (as allowed by the project statement). This gives:
\begin{itemize}
    \item confidentiality in transit,
    \item integrity of command/response messages,
    \item endpoint authentication.
\end{itemize}

The channel does \emph{not} replace application-level flow control. It prevents transport attacks, not semantic leaks caused by accepted computations.

\subsection{Security Goals}

We prove command-level preservation of these goals:
\begin{itemize}
    \item \textbf{G1 Confidentiality}: no illegal read-down from high-confidentiality labels.
    \item \textbf{G2 Integrity}: no illegal write-up into high-integrity state.
    \item \textbf{G3 Secure program execution}: only flow-safe user programs are executed.
    \item \textbf{G4 Controlled declassification}: confidentiality relaxation occurs only with proper authority and approved transforms.
    \item \textbf{G5 Accountability}: every declassification is logged with actor, authority, and justification.
\end{itemize}
