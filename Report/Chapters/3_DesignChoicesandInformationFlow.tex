\section{Design Choices and Information-Flow Argument}

\subsection{Design Scope and Priority}

The project prioritizes formal precision over feature breadth. We therefore choose a compact model with:
\begin{itemize}
    \item one fixed actor universe $\mathcal{A}$,
    \item decentralized labels on all persistent objects,
    \item white-box user programs only,
    \item a small trusted set of server-side declassifiers.
\end{itemize}

This avoids unverifiable corner cases from arbitrary black-box user code.

\subsection{Why a Decentralized Label Model}

Instead of a single global low/medium/high lattice, we use Myers-Liskov decentralized labels where different owners can impose independent constraints. This is important in collaborative healthcare data, where a record can be constrained by hospital policy, doctor policy, and legal policy at once.

\subsection{Flow Order and Program Rules}

We write $L_1 \sqsubseteq L_2$ when information is allowed to flow from label $L_1$ to $L_2$, respecting both confidentiality and integrity components.

Core program rules used by the server checker:
\[
\frac{\Gamma \vdash e : L_e \qquad pc \sqcup L_e \sqsubseteq \Gamma(x)}{\Gamma,pc \vdash x := e}
\]

and for conditionals, $pc$ is raised with the label of the guard expression. This blocks both explicit and implicit leaks.

\subsection{Why White-Box Programs}

Users upload source code plus declared argument labels. The server performs static checking before execution.

Reasoning:
\begin{itemize}
    \item black-box code cannot be analyzed for illegal internal flows,
    \item rejecting unsafe code before runtime is stronger than post-hoc monitoring,
    \item the resulting guarantee is compositional with API-level checks.
\end{itemize}

\subsection{Declassification Design Choice}

Declassification is only allowed in trusted server transformations, not in arbitrary user code. Each declassification requires:
\begin{itemize}
    \item explicit target policy,
    \item proof that caller has required authority for each relaxed owner policy,
    \item transform-specific constraints (for example minimum cohort size),
    \item immutable audit logging.
\end{itemize}

This follows the Myers-Liskov idea that confidentiality relaxation must be explicit and authority-controlled.

\subsection{Attack-Driven Justification}

\textbf{A1: direct copy leak}.\
Blocked by assignment rule when destination confidentiality would allow extra readers.

\textbf{A2: implicit control leak}.\
Blocked because $pc$ joins into assignments in guarded code.

\textbf{A3: integrity poisoning}.\
Blocked because flows into high-integrity destinations require sufficiently trusted sources.

\textbf{A4: unauthorized downgrade}.\
Blocked because \texttt{DECLASSIFY\_AND\_RELEASE} requires authority checks and policy validation.

\subsection{Boundaries of the Argument}

Our proof obligations do not cover compromised trusted server code or covert channels outside the language and API model. Stating this boundary keeps claims accurate and grade-relevant.
