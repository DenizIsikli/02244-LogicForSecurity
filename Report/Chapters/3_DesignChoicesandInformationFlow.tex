\section{Design Choices and Information-Flow Argument}

\subsection{Why a Three-Level Lattice}

We use:
\[
\textbf{Low} \sqsubseteq \textbf{Medium} \sqsubseteq \textbf{High}
\]
because it matches the domain policy exactly (public, friends, private) while still being simple enough for static checking and manual reasoning.

Security relevance of this choice:
\begin{itemize}
    \item it captures collaboration (Medium) without collapsing into all-or-nothing secrecy,
    \item it avoids ad hoc exceptions: every flow is judged by the same order relation,
    \item it makes violations explicit as lattice-order failures.
\end{itemize}

\subsection{Core Typing Rules and Their Purpose}

For expressions:
\[
\frac{\Gamma \vdash e_1 : \tau_1 \qquad \Gamma \vdash e_2 : \tau_2}{\Gamma \vdash e_1 \oplus e_2 : \tau_1 \sqcup \tau_2}
\]
The join reflects that combined expressions depend on both inputs.

For assignments:
\[
\frac{\Gamma \vdash e : \tau_e \qquad \tau_e \sqsubseteq \tau_x}{\Gamma \vdash x := e}
\]
This is the primary explicit-flow barrier. A violation is not a policy warning; it is a static rejection.

For conditionals with program counter $pc$:
\[
\text{required: } (pc \sqcup \tau_e) \sqsubseteq \tau_x
\]
This blocks implicit flows where branch structure reveals secrets.

\subsection{Design Decisions and Security Effects}

\textbf{Decision D1: Type-check before execution}.\
Reason: if a malicious program runs first, leakage may be irreversible.\
Effect: unsafe code never executes, satisfying G1 by construction.

\textbf{Decision D2: Keep authorization and typing separate}.\
Reason: access control answers \emph{who may request}; typing answers \emph{what information may influence what}.\
Effect: protects against both external access violations and insider exfiltration code.

\textbf{Decision D3: Use TLS-style secure channels for transport}.\
Reason: without authenticated confidential channels, attacker can read or alter traffic regardless of internal typing.
Effect: supports G1 and G3 in transit, while typing enforces them in computation.

\textbf{Decision D4: Declassification is explicit and narrowly scoped}.\
Reason: practical systems require release of useful low-level aggregates.
Effect: every High $\rightarrow$ Low release is intentional, reviewable, and auditable (G4).

\subsection{Why Specific Attacks Are Prevented}

\textbf{Attack A1: Direct exfiltration}. Attempt: assign private field to public output.\
Blocked because assignment requires High $\sqsubseteq$ Low, which is false.

\textbf{Attack A2: Branch leak}. Attempt: branch on secret and write branch-dependent value to Low variable.\
Blocked because $pc=\text{High}$ in the branch; then $(pc\sqcup\text{Low})\sqsubseteq\text{Low}$ fails.

\textbf{Attack A3: Network tampering/replay}. Attempt: modify or replay command messages.\
Blocked at channel layer by integrity/authentication checks, provided endpoint keys and certificate validation are correct.

\textbf{Attack A4: "Legitimate" statistical leak}. Attempt: query repeatedly until individual values can be inferred.\
Mitigated by approved declassification transforms and privacy budget constraints (Chapter 6), not by base typing alone.

\subsection{Limitations and Honest Boundaries}

The argument intentionally does not claim protection against:
\begin{itemize}
    \item compromised trusted server code,
    \item covert channels outside the model (hardware timing, cache state),
    \item misuse of declassification policy if governance is weak.
\end{itemize}

Stating these limits strengthens correctness of claims and keeps the proof obligations aligned with the course framework.
